= HAL-DIscovering SHell scripts
:toc: left
:toc-title: Contents
:toclevels: 3
:icons: font
:sectnums:

HALDiSh is a Bash library and toolkit for making HTTP requests, navigating
https://stateless.co/hal_specification.html[HAL (Hypertext Application Language)]
documents, and performing common shell-scripting tasks.  Everything ships as a
single self-inflatable `.run` archive that requires nothing beyond Bash 4 and
standard UNIX tools; optional `yq` or `jq` unlocks YAML, XML, and JSON
document navigation.  It is aimed at shell scripters, API developers, and CI
pipelines that need to drive or document hypermedia APIs without introducing
heavyweight runtime dependencies.

== Obtaining the archive

=== From GitHub Releases

Download the latest `.run` archive from the
https://github.com/C06A/HALDiSh/releases[Releases page]:

[source,bash]
----
curl -LO https://github.com/C06A/HALDiSh/releases/latest/download/HALDiSh-<version>.run
----

=== From Maven Central

The archive is also published to https://central.sonatype.com/artifact/com.helpchoice/haldish/versions[Maven Central] under the coordinates
`com.helpchoice:haldish:<version>`:

[source,bash]
----
curl -LO "https://repo1.maven.org/maven2/com/helpchoice/haldish/<version>/haldish-<version>.run"
----

=== As a build dependency

==== Gradle

Add a dedicated configuration for the `.run` artifact and register an install
task.  The installed library is then available to any shell task that sources
`env.sh`.

[source,kotlin]
----
// build.gradle.kts

repositories {
    mavenCentral()
}

val haldish: Configuration by configurations.creating

dependencies {
    implementation("com.helpchoice.hal:haldish:<version>@run")
}

val installHaldish by tasks.registering {
    inputs.files(haldish)
    val installDir = layout.buildDirectory.dir("haldish")
    outputs.dir(installDir)

    doLast {
        val dir = installDir.get().asFile
        dir.mkdirs()
        exec {
            commandLine("bash", haldish.singleFile.absolutePath,
                        "--prefix", dir.absolutePath)
        }
    }
}
----

After the task runs, the library is at `build/haldish/`.

Declare the dependency with type `run` and use the `maven-dependency-plugin`
to copy it, then invoke the installer with the `exec-maven-plugin`:

== Installation

The `.run` file is a self-inflatable archive.  Run it directly with Bash:

[source,bash]
----
bash HALDiSh-<version>.run
----

By default the library is extracted to `~/.local/lib/haldish`.  Pass a custom
installation location with `--prefix`:

[source,bash]
----
bash HALDiSh-<version>.run --prefix /opt/haldish
----

The installer performs the following steps:

1. Extracts all scripts to the prefix directory.
2. Checks that Bash 4 or later is available.
3. Creates the HTTP method entry-points (`GET`, `POST`, `PUT`, `PATCH`,
   `OPTIONS`, `DELETE`) as hardlinks to the underlying `httpreq.sh` script.

== Activation

Source `env.sh` at the start of any shell session or script that uses the
library.  This loads all utility functions and adds the library directory to
`PATH`:

[source,bash]
----
source ~/.local/lib/haldish/env.sh
----

After sourcing:

* All `hal::*` functions are available in the current shell.
* The library directory is prepended to `PATH`, so scripts such as `uritemplate.sh`,
  `hal.sh`, `adocs.sh`, the HTTP method entry-points, and other can be invoked by name.
* The `HAL_LIB_DIR` environment variable is exported and points to the
  installation directory.  Scripts that need to locate the library at runtime
  can read this variable.

`env.sh` must be sourced, not executed directly.  If sourced from a context
where the integrity check fails, it returns exit code 1 without loading
anything.

== `setup.sh` — post-install configuration

Executed automatically by the self-inflatable archive after extraction.  Can
also be run manually:

[source,bash]
----
bash <prefix>/setup.sh [--prefix <dir>]
----

`setup.sh` verifies the installation, renames `httpreq.sh` to `.httpreq.sh`,
creates the `GET`, `POST`, `PUT`, `PATCH`, `OPTIONS`, and `DELETE` hardlinks,
and generates the integrity manifest.  It prints colourised progress to
stdout.


== `hal.sh` — HAL document navigator

Navigate and extract values from
https://stateless.co/hal_specification.html[HAL] documents in JSON, YAML, or
XML format.  Requires `yq` (mikefarah/yq v4) for JSON, YAML and XML files,
and fails back on `jq`, which supports JSON-only use.

=== Usage

[source,bash]
----
hal.sh <file>                                   # interactive
hal.sh <file> links      [rel [N] [field]]      # non-interactive
hal.sh <file> embeddeds  [rel [N] [args...]]    # non-interactive
hal.sh <file> properties [key [args...]]        # non-interactive
hal.sh <file> docs                              # interactive docs browser
hal.sh <file> docs       <rel>                  # non-interactive: print doc URL
----

=== Non-interactive sub-commands

[cols="1,3",options="header"]
|===
|Sub-command |Description

|`links`
|Extract from `_links`.  With no further arguments, prints all relation names.
With `rel`, returns the link object for that relation.  Append `N` for a
specific element of an array-valued link.  Append `field` (e.g. `href`,
`templated`, `title`) to extract a single field from the link object.

|`embeddeds`
|Extract from `_embedded`.  With no further arguments, prints all relation
names.  With `rel`, returns the embedded resource (or its array).  Append `N`
to select an array element, then optionally continue traversing with further
sub-commands or field names.

|`properties`
|Extract top-level properties (those outside `_links` and `_embedded`).
With no further arguments, prints all property names.  Append `key` to
retrieve a value, then optionally traverse further with additional keys or
numeric indices.

|`docs`
|With no `rel`, opens an interactive documentation browser listing the curie-defined
relations available in the current resource.  With `rel` (curie-prefixed or local name),
prints the documentation URL to stdout.
|===

=== Interactive mode

Invoking `hal.sh <file>` with no sub-command opens a menu-driven navigator:

* At the top level you are offered the choices available in the document
  (`links`, `embeddeds`, `properties`, `print`, `exit`).
* Descend into any section and navigate deeper; choose `return` to go back up.
* Choosing `print` writes the JSON of the current node to stdout.
* Choosing `quit` (from nested menus) or `exit` (from the top level) prints
  the jq/yq filter expression for the current position to stdout and exits.

=== stdin / stdout / exit codes

[cols="1,3",options="header"]
|===
|Channel |Content

|stdin
|Not used; the document is read from the file argument.

|stdout
|Non-interactive: the extracted value (raw scalar or compact JSON).
Interactive: the chosen jq/yq filter expression on quit.

|stderr
|Error messages; interactive menus and prompts.

|Exit 0
|Success.

|Exit 1
|File not found, unknown sub-command, traversal error, or no parser available.
|===

=== Examples

[source,bash]
----
# List all link relations
hal.sh response.body links

# href of the self link
hal.sh response.body links self href

# Second embedded "items" resource
hal.sh response.body embeddeds items 1

# Value of the "total" property
hal.sh response.body properties total

# Nested property traversal (array index then key)
hal.sh response.body properties tags 0
----


== `nahal.sh` — interactive HAL API browser

Drive a live HAL API from the terminal.  `nahal.sh` fetches a resource,
classifies the response by `Content-Type`, and presents menu-driven navigation
of its links, embedded resources, properties, and documentation.  Following a
link sends a new request (any HTTP method, with an optional body), and the whole
session is recorded as a re-runnable `session.sh` script.

Requests are made with the HTTP method commands (`GET`, `POST`, …) and responses
are navigated with `hal.sh`, so `nahal.sh` needs the HALDiSh environment active
(`source env.sh`) plus `curl` and `yq` or `jq`.

=== Usage

[source,bash]
----
nahal.sh <URL>                        # start from a URL
nahal.sh <link-text>                  # start from a HAL link object (JSON/XML/YAML)
nahal.sh <resource-file> [path…]      # start from a link extracted from a file
----

For the file form, `path` is a `hal.sh` link path, e.g. `links self` or
`embeddeds items 0 links next`.

=== Session directory

Each run creates a `nahal_<timestamp>/` directory beside the working directory.
Every request writes a file group there, renamed to a predictable base
`step_<N>` (`step_1.body`, `step_1.headers`, `step_1.status`, …), and the session
log is written to `nahal_<timestamp>/session.sh`.

=== Response classification

[cols="1,3",options="header"]
|===
|Content-Type |Handling

|`application/hal+json`, `application/hal+xml`, `application/hal+yaml`,
 `application/json`, `application/xml`, `application/yaml`
|Navigate as a HAL resource — or, for a top-level array, a list of resources.

|`text/*`
|Print the content, or re-parse it as a HAL resource.

|anything else
|Offer to open the file with the system default application (`open`/`xdg-open`).
|===

=== Interactive navigation

The resource menu offers only the sections the resource actually has:

* `links` — browse `_links`; pick a relation (templated links are marked `{T}`),
  choose an element for array-valued links, then *follow* it or *show link
  details*.
* `embedded` — descend into `_embedded` resources (selecting an index for arrays).
* `properties` — traverse the non-HAL properties (objects, arrays, scalars).
* `docs` — shown only when the resource has a `curies` array *and* at least one
  relation uses a defined CURIE prefix; resolves the curie template and opens the
  documentation page in the browser.
* `print resource` — pretty-print the current resource.
* `back` / `quit` — go up one level, or end the session.

A top-level array of resources is listed by element (showing each `self` href);
choose one to navigate it as a resource.

=== Following a link

Choosing *follow* prompts for the HTTP method from a menu of the standard verbs
(`GET POST PUT PATCH OPTIONS DELETE HEAD`) plus *Other*, which accepts any
RFC 7230 method token and upper-cases it.  Methods that are not installed
commands (e.g. `HEAD` and custom verbs) are dispatched through an on-demand
`./<METHOD>` link created in the session directory.

For methods other than `GET`, `HEAD`, and `OPTIONS`, a request-body menu offers
inline text, a text file, a URL-encoded string, multipart files, a binary file,
or a raw upload — the same `-a`/`-u`/`-f`/`-b`/`-r` inputs as `httpreq.sh`.  A
dropped `file://` path (for example from a macOS Finder drag) is accepted and
percent-decoded.

=== Session replay

`session.sh` reproduces the session without `nahal.sh`: each step extracts the
next link with `hallink.sh`, sends it through the method command's `--link` mode,
and renames the response files to the same `step_<N>` base.

[source,bash]
----
(HTTP_IN_HEADERS="Accept:application/hal+json, …"

  # initial request
  GET http://api.example.com/ \
    | rename.sh step_1

  # follow 'orders'
  hallink.sh step_1.body links orders \
    | GET --link \
    | rename.sh step_2
)
----

`Accept` is taken from the link's `type` (falling back to the HAL list when the
link has none); a `Content-Type` is added for body requests; consecutive requests
that share the same headers are grouped in one `HTTP_IN_HEADERS` subshell.
Replaying requires the HALDiSh environment on `PATH` — run `source env.sh` first.

=== Examples

[source,bash]
----
# Browse an API from its entry point
nahal.sh https://api.example.com/

# Start from the "self" link extracted from a saved response
nahal.sh response.body links self

# Replay a recorded session
source env.sh
bash nahal_20260603T185734/session.sh
----


== `hallink.sh` — resolve a HAL link object's href

Resolves a HAL link object's `href` field, expanding URI templates when the
link carries `"templated": true`.  Accepts a link object directly or navigates
to one through a HAL document file.  Output format matches the input format
(JSON → JSON, YAML → YAML, XML → XML).

Requires `yq` (mikefarah/yq v4) or `jq` for JSON; `uritemplate.sh` on PATH.

=== Usage

[source,bash]
----
hallink.sh --link [<json|xml|yaml>|@<file>] [var=value ...]
hallink.sh --link                           [var=value ...]  # link from stdin
hallink.sh <file-or-basename> <hal-path>    [var=value ...]
----

`hal-path`: `links <rel> [N]`  or  `embeddeds <rel> [N] links <rel2> [N2]`

`--link` accepts an inline JSON, YAML, or XML link object, a path prefixed with
`@` to read from a file, or reads from stdin when no argument follows `--link`.

File basenames (no `/`) are resolved in the current directory against the
extensions `.json`, `.xml`, `.yaml`, `.yml`, `.body` in that order.

Variable bindings (`var=value`) follow the same syntax as `uritemplate.sh`;
see <<_uritemplate_sh_rfc_6570_uri_template_expander,Variable binding syntax>>.

=== Exit codes

[cols="1,3",options="header"]
|===
|Code |Meaning

|0 |Success.
|1 |Usage or argument error.
|2 |File not found.
|3 |Link not found or missing `href`.
|4 |Required tool not available.
|===

=== Examples

[source,bash]
----
# Resolve the href of the self link
hallink.sh resource.json links self

# Expand a templated link with query variables
hallink.sh resource.json links search 'q=widgets' 'page=2'

# Resolve from an embedded resource
hallink.sh resource.json embeddeds items 0 links self

# Pass a link object inline (template expansion)
hallink.sh --link '{"href":"/api{?q}","templated":true}' 'q=hello'

# Read link from a file
hallink.sh --link @order-link.json

# Pipe the resolved link into an HTTP request
hallink.sh resource.json links next \
  | GET --link
----


== `haldoclink.sh` — emit a documentation link for a HAL link relation

Resolves the documentation URL for a HAL link relation by expanding the
matching curie template, then outputs a HAL link object with that URL as
`href` and `"type":"text/html"`.

Curie lookup starts at the deepest embedded resource that contains the target
link and walks up through each enclosing embedded resource to the root, using
the first ancestor whose `_links.curies` defines the required prefix.

The relation name may be given as a full curie-prefixed key (e.g. `doc:orders`)
or just the local name (e.g. `orders`).  When no prefix is supplied the script
scans the containing resource's `_links` for a key whose suffix matches.

Output format matches the input format (JSON → JSON, YAML → YAML, XML → XML).

Requires `yq` (mikefarah/yq v4) or `jq` for JSON; `uritemplate.sh` on PATH.

=== Usage

[source,bash]
----
haldoclink.sh <file-or-basename> <hal-path>
----

`hal-path`: `links <rel>`  or  `embeddeds <rel> [N] links <rel2>`

File basenames are resolved using the same extension search order as
<<_hallink_sh_resolve_a_hal_link_object_s_href,`hallink.sh`>>.

=== Exit codes

[cols="1,3",options="header"]
|===
|Code |Meaning

|0 |Success.
|1 |Usage or argument error.
|2 |File not found.
|3 |Relation not found, or no curie for its prefix anywhere in the resource stack.
|4 |Required tool not available.
|===

=== Examples

[source,bash]
----
# Documentation link for a root-level relation (explicit curie prefix)
haldoclink.sh resource.json links doc:orders
# → {"href":"https://example.com/docs/orders","type":"text/html"}

# Same result using just the local name
haldoclink.sh resource.json links orders

# Documentation for a relation in an embedded resource
haldoclink.sh resource.json embeddeds orders 0 links ns:detail

# The curie may be defined at root even when the link lives deep
haldoclink.sh resource.json embeddeds orders 0 embeddeds items 0 links doc:part

# Open the documentation page directly
haldoclink.sh resource.json links doc:orders \
  | jq -r .href | xargs open
----


== `halprepend.sh` — prepend a base URL to a HAL link's href

Replaces a HAL link object's `href` field with `<base> + <href>`, leaving all
other fields (`title`, `type`, `templated`, …) unchanged.  Accepts a link
object directly or navigates to one through a HAL document file.  Output
format matches the input format (JSON → JSON, YAML → YAML, XML → XML).

Requires `yq` (mikefarah/yq v4) or `jq` for JSON.

=== Usage

[source,bash]
----
halprepend.sh <base> --link [<json|xml|yaml>|@<file>]
halprepend.sh <base> --link                             # link from stdin
halprepend.sh <base> <file-or-basename> <hal-path>
----

`hal-path`: `links <rel> [N]`  or  `embeddeds <rel> [N] links <rel2> [N2]`

File basenames are resolved using the same extension search order as
<<_hallink_sh_resolve_a_hal_link_object_s_href,`hallink.sh`>>.

=== Exit codes

[cols="1,3",options="header"]
|===
|Code |Meaning

|0 |Success.
|1 |Usage or argument error.
|2 |File not found.
|3 |Link not found or missing `href`.
|4 |Required tool not available.
|===

=== Examples

[source,bash]
----
# Prepend a base URL to a relative href
halprepend.sh 'https://api.example.com' resource.json links self
# → {"href":"https://api.example.com/api/r",...}

# Work with an inline link object
halprepend.sh 'https://api.example.com' --link '{"href":"/orders","title":"Orders"}'

# Read the link from stdin
echo '{"href":"/items"}' | halprepend.sh 'https://api.example.com' --link

# Convert a server-relative href into an absolute URL before following it
link=$(halprepend.sh 'https://api.example.com' resource.json links next)
hallink.sh --link "$link" | jq -r .href | xargs GET
----


== HTTP client — `httpreq.sh`

After activation, the HTTP method entry-points (`GET`, `POST`, `PUT`, `PATCH`,
`OPTIONS`, `DELETE`) are on `PATH` and can be called directly.  They are all
hardlinks into a single underlying script.

=== Usage

[source,bash]
----
GET  <url> [flags...]
POST <url> [flags...]
GET  --  [flags...]              # URL read from first stdin line
GET  --link <json> [flags...]    # HAL link object: href → URL, type → Accept header
GET  --link @<file> [flags...]   # HAL link from file
GET  --link [flags...]           # HAL link from stdin
----

`--link` extracts `href` as the request URL and, when the link object carries a
`type` field, injects an `Accept: <type>` request header automatically.

=== Output files

Each invocation writes a group of files named `<domain>_<timestamp-ms>.*` in
the current directory and prints the base name to stdout, allowing the result
to be piped directly to `rename.sh`, `prettyprint.sh`, `cleanup.sh`, etc.

[cols="1,3",options="header"]
|===
|Extension |Content

|`.url`
|The requested URL (no trailing newline).

|`.curl`
|Shell-quoted `curl` command that exactly replays the request, formatted with
one flag per continuation line for readability.

|`.code`
|The numeric HTTP status code (e.g. `200`).

|`.status`
|HTTP status code with name (e.g. `200 (OK)`).

|`.headers`
|Response headers, one `Name: Value` pair per line (status line and
`Set-Cookie` headers excluded; compatible with `HTTP_IN_HEADERS_FILE` format).

|`.cookies`
|Response cookies extracted from `Set-Cookie` headers, one `name=value` per
line (compatible with `HTTP_IN_COOKIES_FILE` format).

|`.body`
|Raw response body.
|===

=== Request body flags

[cols="1,3",options="header"]
|===
|Flag |Description

|`-a [text]`
|Plain-text or JSON body (`--data`).  Omit text to read from stdin.

|`-u [text]`
|URL-encoded body (`--data-urlencode`).  Repeatable for multiple fields.
Omit text to read from stdin.

|`-f [name=]file`
|Multipart file upload (`--form name=@file`).  `name` defaults to the file's
basename when omitted.  Omit `file` entirely to send stdin as a raw binary
body instead of multipart.  Repeatable for multiple parts.

|`-F name=value`
|Multipart text field (`--form name=value`).  Repeatable for multiple fields.

|`-b [file]`
|Binary body from file (`--data-binary @file`).  Omit file to read from stdin.

|`-r [file]`
|Raw upload (`--upload-file`).  Omit file to read from stdin.

|`-i`
|Include `-i` in the saved `.curl` replay file so the replay shows response
headers.
|===

=== Request headers and cookies

Set request headers via `HTTP_IN_HEADERS` (one `Name: Value` per line) or
point `HTTP_IN_HEADERS_FILE` at a file with the same format.  Cookies work the
same way via `HTTP_IN_COOKIES` / `HTTP_IN_COOKIES_FILE` (one `name=value` per
line):

[source,bash]
----
export HTTP_IN_HEADERS="Authorization:Bearer $TOKEN
Accept:application/hal+json"

GET 'https://api.example.com/orders'
----

=== Pipeline example

[source,bash]
----
source ~/.local/lib/haldish/env.sh

base=$(GET 'https://api.example.com/orders')
echo "Status: $(cat "${base}.status")"
hal.sh "${base}.body" properties total
----

== `uritemplate.sh` — RFC 6570 URI Template expander

Expands https://www.rfc-editor.org/rfc/rfc6570[RFC 6570] URI Templates.
Requires Bash 4.0 or later (for associative arrays).

=== Usage

[source,bash]
----
uritemplate.sh <template> [var_binding...]   # template as first argument
uritemplate.sh -          [var_binding...]   # template read from first stdin line
echo '<template>' | uritemplate.sh           # template from stdin; no bindings
----

Undefined variables are silently omitted from the expansion.

=== Variable binding syntax

[cols="1,2",options="header"]
|===
|Syntax |Type

|`name=value`
|String variable.  Repeat with the same name to build a list automatically
(first occurrence sets a string; the second occurrence promotes it to a list).

|`name[]=value`
|List append.  Preferred explicit syntax for list values.

|`name[key]=value`
|Map entry.
|===

=== Operator reference

[cols="1,1,3",options="header"]
|===
|Operator |Prefix / separator |Behaviour

|(none)
|none / `,`
|Simple expansion; values are percent-encoded.

|`+`
|none / `,`
|Reserved expansion; reserved characters pass through unencoded.

|`#`
|`#` / `,`
|Fragment expansion; reserved characters pass through unencoded.

|`.`
|`.` / `.`
|Label expansion; dot-prefixed and dot-separated.

|`/`
|`/` / `/`
|Path segment expansion; slash-prefixed and slash-separated.

|`;`
|`;` / `;`
|Path-style parameter expansion; named pairs with semicolon separator.

|`?`
|`?` / `&`
|Query string expansion; `key=value` pairs.

|`&`
|`&` / `&`
|Query continuation; appends `&key=value` pairs.
|===

Append `*` to a variable name to explode lists and maps into separate
components separated by the operator separator.  Append `:N` to truncate a
string variable to its first N characters.

=== Examples

[source,bash]
----
uritemplate.sh 'https://example.com/users/{id}' 'id=42'
# → https://example.com/users/42

# Query string
uritemplate.sh '{?q,lang}' 'q=hello world' 'lang=en'
# → ?q=hello%20world&lang=en

# Reserved expansion (slashes preserved)
uritemplate.sh 'https://example.com{+path}' 'path=/foo/bar'
# → https://example.com/foo/bar

# List via explicit append syntax
uritemplate.sh '{?tags*}' 'tags[]=red' 'tags[]=green' 'tags[]=blue'
# → ?tags=red&tags=green&tags=blue

# Path segments from repeated plain key
uritemplate.sh '{/segments*}' 'segments=a' 'segments=b' 'segments=c'
# → /a/b/c

# Map expansion
uritemplate.sh '{?filters*}' 'filters[status]=active' 'filters[page]=1'
# → ?filters=active&filters=1

# Template from stdin
echo '/items/{id}' | uritemplate.sh - 'id=7'
# → /items/7
----


== `rename.sh` — rename a request-file group

Renames all files that share a base name, preserving their extensions.

[source,bash]
----
rename.sh <new-name> <old-name>
rename.sh <new-name>               # old-name read from stdin
----

[cols="1,3",options="header"]
|===
|Channel |Content

|stdin
|Old base name when not given as an argument.

|stdout
|New base name on success (one line).

|Exit 0
|All files renamed.

|Exit 1
|Wrong number of arguments or no files found matching `<old-name>.*`.
|===

Pipeline example:

[source,bash]
----
GET 'https://api.example.com/orders/1' | rename.sh order-1 | adoc.sh
----


== `prettyprint.sh` — content-type detector and pretty-printer

Inspects the content of `<base>.<src-ext>` (default source extension:
`.body`), identifies the format, copies or moves it to `<base>.<detected-ext>`,
and reformats JSON, YAML, and XML to human-readable pretty-print form.  Other
text content is converted to UTF-8.

=== Usage

[source,bash]
----
prettyprint.sh [options] [base_name...]
printf 'base1\nbase2\n' | prettyprint.sh [options]
----

Options are _positional_ and apply to all base names that follow them:

[cols="1,3",options="header"]
|===
|Option |Effect

|`-c`
|Copy mode: keep the source file after writing the formatted output.
This is the default.

|`-m`
|Move mode: remove the source file after the formatted file is written.

|`-e <ext>`
|Use `.<ext>` as the source extension instead of `.body` for all following
base names.  The leading dot is optional (`-e json` and `-e .json` are
equivalent).
|===

=== stdin / stdout / exit codes

[cols="1,3",options="header"]
|===
|Channel |Content

|stdin
|Base names (one per line) when none are given on the command line.

|stdout
|Base name for each processed file (one per line).

|stderr
|Progress, warnings, and error messages (uses `hal::log::*` if loaded,
otherwise plain `[INFO]`/`[WARN]`/`[ERR ]` prefixes).

|Exit 0
|All files processed.

|Exit 1
|Source file not found, or `-e` supplied without an extension argument.
|===

=== Detected formats

[cols="1,3",options="header"]
|===
|Category |Extensions assigned

|Structured text (reformatted)
|`json`, `yaml`, `xml`, `html`

|Other text
|`csv`, `txt`, `svg`

|Images
|`jpg`, `png`, `gif`, `webp`, `bmp`, `tif`

|Office (OOXML)
|`docx`, `xlsx`, `pptx`

|Office (legacy binary)
|`doc`, `xls`, `ppt`

|Office (ODF)
|`odt`, `ods`, `odp`

|Documents / e-books
|`pdf`, `epub`

|Archives
|`zip`, `gz`, `bz2`, `xz`, `tar`

|Unknown binary
|`bin`
|===

Pretty-print tools are chosen automatically (first available wins):

[cols="1,2",options="header"]
|===
|Format |Tools tried in order

|JSON
|`jq`, `python3 -m json.tool`

|XML / HTML
|`xmllint --format`, `python3 xml.dom.minidom`

|YAML
|`yq`, `python3 yaml` (PyYAML)
|===

When no formatter is available the file is still copied or moved as-is and a
warning is emitted.

=== Examples

[source,bash]
----
# Pretty-print the response body from an HTTP request
base=$(GET 'https://api.example.com/orders/1')
prettyprint.sh "$base"
# Creates order.json (or .xml, .yaml, .html, …)

# Move mode: remove .body after conversion
prettyprint.sh -m "$base"

# Mixed: copy first response, move subsequent ones
prettyprint.sh "$base1" -m "$base2" "$base3"

# Source is already named .json
prettyprint.sh -e json "$base"

# Pipeline: fetch → pretty-print → HAL navigate
base=$(GET 'https://api.example.com/items')
prettyprint.sh -m "$base" | xargs -I{} hal.sh {}.json properties total
----


== `cleanup.sh` — request-file group cleaner

Deletes all files that share a base name except those whose extension is in the
keep list.  Designed to remove intermediate HTTP client output files (`.curl`,
`.status`, `.headers`, `.cookies`) while preserving the files you want to keep
(e.g. `.body`, `.json`).

=== Usage

[source,bash]
----
cleanup.sh <base-name> [keep-ext...]
cleanup.sh -- [keep-ext...]              # base-name read from stdin
----

With no keep-extensions every matching `<base-name>.*` file is deleted.
Extensions are given without the leading dot.

=== stdin / stdout / exit codes

[cols="1,3",options="header"]
|===
|Channel |Content

|stdin
|Base name (when `--` is the first argument).

|stdout
|Base name (one line), whether or not any files were deleted.

|stderr
|Usage message on error.

|Exit 0
|Success (including when no matching files exist).

|Exit 1
|No arguments supplied.
|===

=== Examples

[source,bash]
----
# Delete everything except the response body
base=$(GET 'https://api.example.com/orders/1')
cleanup.sh "$base" body

# Keep body and curl replay; delete headers, cookies, status
cleanup.sh "$base" body curl

# Delete all matching files
cleanup.sh "$base"

# Pipeline: fetch → pretty-print → keep only the formatted file
GET 'https://api.example.com/orders' \
  | prettyprint.sh -m \
  | cleanup.sh -- json
----

== `adoc.sh` — AsciiDoc region generator

Wraps files that share a base name in AsciiDoc `tag::` / `end::` regions so
they can be included directly in documentation with the `include::` directive.
Designed to work with the output file groups produced by the HTTP client
(`.curl`, `.status`, `.headers`, `.cookies`, `.body`), but accepts any file
groups.

=== Usage

[source,bash]
----
adoc.sh [-a <file>] <base>...
printf "base1\nbase2\n" | adoc.sh [-a <file>]
----

[cols="1,3",options="header"]
|===
|Option |Description

|`-a <file>`
|Append the generated AsciiDoc content to `<file>` instead of writing to
stdout.  In this mode the base name of each processed group is printed to
stdout (for piping into further tools).  If `<file>` does not yet exist or is
empty, a document header is prepended automatically.
|===

=== Output format

For each base name, `adoc.sh` finds all files matching `<base>.*` in the
current directory and emits a level-2 heading for the group, a level-3 heading
for each file, and a source block wrapping the file content between
`// tag::<filename>[]` and `// end::<filename>[]` markers.

=== stdin / stdout / exit codes

[cols="1,3",options="header"]
|===
|Channel |Content

|stdin
|Base names (one per line) when none are given as arguments.

|stdout
|AsciiDoc text (default mode) or base name per group (`-a` mode).

|stderr
|Not used for normal output.

|Exit 0
|All groups processed successfully.

|Exit 1
|`-a` specified without a filename argument.
|===

=== Including regions in documentation

[source,asciidoc]
------
The following request was captured with HALDiSh:

[source,bash]
----
\include::responses.adoc[tag=jsonplaceholder.typicode.com_1711234567890.curl]
----

The server responded with HTTP `include::responses.adoc[tag=jsonplaceholder.typicode.com_1711234567890.status]`:

[source,json]
----
\include::responses.adoc[tag=jsonplaceholder.typicode.com_1711234567890.body]
----
------

=== Pipeline example

[source,bash]
----
# Capture a request, rename the files, and append AsciiDoc regions
GET 'https://api.example.com/orders/1') \
  | rename.sh get-order-1 "$base" \
  | adoc.sh -a docs/examples.adoc >/dev/null
----

The last redirect will drop the printed name into the 'sink'.


== `hal_utils.sh` — utility function library

Source this file to load all `hal::*` helper namespaces.  It is loaded

source /path/to/haldish/hal_utils.sh

The library is double-source safe: sourcing it a second time is a no-op.

[cols="1,2,1",options="header"]
|===

|`hal::str::trim <string>`

|`hal::str::upper <string>`
|Convert to uppercase.

|`hal::str::lower <string>`
|Convert to lowercase.

|`hal::str::length <string>`

[cols="1,2,1",options="header"]
|===
|Function |Description |Return value

|Exit 0 if found, 1 otherwise. No stdout output.

[cols="1,2",options="header"]
|===
|Function |Description

|Return 0 if path exists (file or directory), 1 otherwise.

|`hal::fs::is_file <path>`

|`hal::fs::is_dir <path>`

=== Logging — `hal::log::*`

All logging functions write to stderr.  Color output is disabled automatically
when stderr is not connected to a terminal.  The verbosity level is controlled
by `HAL_LOG_LEVEL` (default: `info`).

==== Log functions

[cols="1,1,2",options="header"]
|===
|Function |Threshold |Description

|`hal::log::trace <message>`
|`trace` (5)
|Dim `[TRC ]` prefix.  Most verbose; useful for step-by-step tracing.

|`hal::log::debug <message>`
|`debug` (4)
|Magenta `[DBG ]` prefix.

|`hal::log::info <message>`
.2+|`info` (3)
|Cyan `[INFO]` prefix.

|`hal::log::ok <message>`
|Green `[ OK ]` prefix.  Shares the `info` threshold with `hal::log::info`.

|`hal::log::warn <message>`
|`warn` (2)
|Yellow `[WARN]` prefix.

|`hal::log::error <message>`
|`error` (1)
|Red `[ERR ]` prefix.

|`hal::log::die <message> [exit-code]`
|always
|Print a red `[ERR ]` line and exit.  Default exit code is 1.  Always prints
regardless of `HAL_LOG_LEVEL`.
|===

==== Log level reference

[cols="1,1,3",options="header"]
|===
|`HAL_LOG_LEVEL` value |Numeric |Messages shown
|`off` or `0` | 0 | `die` *only*
|`error`, `err`, or `1` | 1 | `error`, `die`
|`warn`, `warning`, or `2` | 2 | `warn`, `error`, `die`
|`info` _(default)_ or `3` | 3 | `info`, `ok`, `warn`, `error`, `die`
|`debug` or `4` | 4 | `debug`, `info`, `ok`, `warn`, `error`, `die`
|`trace` or `5` | 5 | All messages
|===

Call `hal::log::init` after changing `HAL_LOG_LEVEL` for the change to take
effect, or pass the desired level as a direct argument:

[source,bash]
----
# Set level via environment variable, then reload
export HAL_LOG_LEVEL=warn
hal::log::init

# Set level as an argument (takes precedence over HAL_LOG_LEVEL)
hal::log::init debug
hal::log::debug "Verbose section starts here"
----


== `menu.sh` — interactive single-selection menu

A keyboard-driven selector that can be composed into any interactive script.

=== Usage

[source,bash]
----
menu.sh <prompt> <option> <option>...   # prompt and options all as arguments
menu.sh <prompt>                        # prompt as argument; options from stdin
menu.sh                                 # first stdin line = prompt; rest = options
----

=== stdin / stdout / exit codes

[cols="1,3",options="header"]
|===
|Channel |Content

|stdin
|Options (and optionally the prompt) when not supplied as arguments.

|stdout
|Text of the chosen option (one line).

|stderr
|Menu display and echo of the chosen key.

|Exit 0
|A valid selection was made.

|Exit 1
|No options were provided.
|===

Selection uses a single keypress: digits `1`–`9` then letters `a`–`z` (up to
35 options per page).  When more than 36 options are present, the menu
paginates at 30 items per page; press `<` or `>` to move between pages.

=== Examples

[source,bash]
----
# All options on the command line
color=$(menu.sh "Pick a color" Red Green Blue Yellow)

# Options piped via stdin
method=$(printf 'GET\nPOST\nPUT\nDELETE\n' | menu.sh "HTTP method")

# Both prompt and options from stdin
env=$(printf 'Target:\ndevelopment\nstaging\nproduction\n' | menu.sh)

# Branching on the selection
action=$(menu.sh "Action" "Show disk usage" "List processes" "Print directory")
case "$action" in
    "Show disk usage")     df -h ;;
    "List processes")      ps aux | head -10 ;;
    "Print directory")     pwd ;;
esac
----
